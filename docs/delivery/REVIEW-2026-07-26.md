## 二、最大的问题：30% 那一栏里最关键的两个指标是空的

赛题原文写得很死：

> 实际效果：30%。……**包括攻击识别准确率、误报漏报情况、风险阻断效果、审计溯源完整性**等量化指标。

你现在交的是：风险阻断效果 ✅（OAR）、审计溯源完整性 ✅（这块做得很好）、
**攻击识别准确率 ❌、误报漏报 ❌**。

我 grep 了两份稿子：`召回` 0 次、`误报` 0 次、`准确率` 0 次。
v0.2 第 148 行还主动写了一句"独立 holdout/formal dual-500 已退役为比赛硬指标"——
这句话对评委的意思就是"我们没有识别率数据"。

### 但数据其实在仓库里

`docs/evidence/gate1-l3-evaluation-2026-06-18.json` 里有个 `gate1_scope` 字段：

```
声明范围（6 个输入攻击族，60 例）
  detection_recall = 1.0      blocking_recall = 1.0      ASR = 0.0
  误报 0/58（FPR 分母为 58 个 expected-allow 负控制 = 76 良性控制减去 18 个 expected non-allow），Wilson 95% 上界 6.21%
  规则层时延 p50 0.02ms / p95 0.04ms
  payload 指纹零重叠的诊断切分：两侧 recall 均 1.0、FPR 均 0.0
```

### 那个难看的 0.3575 是归属误配，不是系统弱

我把 `by_attack_type` 全拆开了：

**命中 100% 的（60 例，0 漏报）**
`dangerous_command` 15/15、`jailbreak_or_prompt_leak` 12/12、`indirect_injection` 10/10、
`forbidden_generation` 8/8、`secret_exfil` 8/8、`pii_leak` 7/7

**全漏的 133 例长这样**
`log_retention_below_6m`（日志留存不足 6 个月）、`encryption_downgrade`（加密降级）、
`restart_requires_approval`（重启需审批）、`cii_external_transfer`（关基外传）、
`malicious_plugin`、`covert_network`、`dependency_typosquat`……

看出来了吗——**这些本来就不是 Gate1 输入规则该管的东西**，
它们归 Gate2（审批）/ Gate3（策略）/ Gate5（沙箱）/ AIBOM（供应链）裁决。
拿注入检测规则去考合规治理题，当然只有 35.75%。

### 改成分层表，同时更诚实、也强得多

| 用例族 | 例数 | 结果 | 裁决关卡 |
|---|---:|---|---|
| 输入攻击族（注入/越狱/危险命令/密钥外泄/PII/违规生成） | 60 | 召回 **100%**、阻断 100%、ASR 0% | Gate1 |
| 治理与策略族（审批/留存/加密/跨域/供应链…） | 133 | 由 Gate2/3/5 + AIBOM 裁决，不计入 Gate1 召回 | 非 Gate1 |
| 负控制（expected allow） | 58 | 误报 **0**（Wilson 95% 上界 6.21%） | — |

**四条边界必须一起写，一条都不能少**：
1. 60 例规模小，只覆盖 6 个族；
2. seed 与规则开发同源，`independent_holdout=false`，那个切分是**诊断性**的，不是独立泛化评估；
3. 报 Wilson 区间，别让点值单独出现；
4. 时延是规则层的，不含模型后端。

写"有范围的 100% + 0 误报 + 置信区间"远好过现在的"什么都不写"。
**这是全篇性价比最高的一处修改，约一页，直击 30%。**

做一张六列表（输入检测 / 工具授权 / 信息流 / 供应链 / **副作用恢复** / 证据链），

**⑤ 14 页用了 30 页预算。** 上面几项加起来约 8 页，v0.2 本身约 22–26 页，正好。别浪费额度。

处理方式：所有边界收进一个"能力边界与不声明事项"的框，正文只写"结果 + 适用范围"，
不写"我们没有 X"。**边界内容一条不减，只改位置和句式。**

这是确定性合成靶场，把两个注入 case 提到 N=10 成本很低，但"10/10"读起来完全不是一个量级。

## 四、D3 视频：现在的脚本有结构性缺陷

现在 8 个镜头全是「身份 → intent-first → Undo → 证据」这条工程闭环，
**没有一秒钟的实拍攻击拦截，也没有 AIBOM 画面**。方向一和方向三在视频里 0 出镜，
OAR 那些数字只以摘要文字出现。

评委打 30% 的时候第一句就是"攻击识别"。视频是他们感知"实际效果"最直接的通道，
让他愿意相信的是**看见攻击被拦下来**，不是看见一个写着 3/3 的 JSON。

完整镜头表在 [执行计划 §7](D1-D3-submission-plan.md)。核心改动：

- 前 4 分钟改成**四方向实拍**：live A/B 注入拦截 → 识别量化表 → 高风险命令拒绝/批准对照 → AIBOM 恶意插件 deny；
- 身份与 Undo 闭环往后挪（它很好，但不该开场就讲 50 秒）；
- kind 七阶段和 compose ps 从逐条展示压缩到合计约 15 秒，腾出的时间正好够新增段落；
- **clean/tampered 验签对照那 30 秒必须留**——一个 exit 0 一个 exit 1，是"审计溯源完整性"最省解释的画面。

几个制作提醒：

- 屏幕上每个数字必须等于 D1 里的数字。**先冻数字，再录。**
- 分 10–12 个 ≤90 秒短片段录，每段一个概念。**先做一次完整的不录制预演**，专门找 UI 崩的地方。
- 终端里露一次 `git rev-parse HEAD` 且与 D1 PDF 上写的 commit 一致——成本近零，可信度加成很大。
- 顺手办件事：赛事保障说了可以答疑，事实源 §8 的 Q6 就是"视频是否有格式要求"。
  **录之前先发邮件问**，别录完了才发现要求不同。
- 现行脚本的 §2 环境准备、§4 失败恢复、§5 合成验收三节都还有效，直接复用。

## 五、关于"先不冻 PDF"——你的直觉方向对，但依赖关系搞反了

你说的是「视频 → PDF」。真正的依赖链是：

> **数字 → 视频 → PDF**

数字才是最上游的约束。如果视频录完之后某个数字变了，你要么重录，
要么让 D1 和视频对不上——而口径漂移正是你自己的 checklist 第 54 行列为红线的东西。

所以答案不是"晚点冻 PDF"，而是**"早冻数字，晚冻 PDF"**：

| 时间 | 做什么 | 冻结点 |

| 7/27–8/2 | 定稿源 + 补那四块内容 + **立刻构建一版扔掉的 PDF** | — |

9/10 发现，成本是整个交付。**这周就跑一版废弃 PDF**，量一下页数。

## 六、关于"vibe 出来的、掌控力低"

这是这个项目最大的实际风险，因为 11 月是**现场答辩**。三件具体的事：

**1）录 D3 就是最好的补掌控力训练。**
你必须手动把系统从头走到尾，还要边走边说清每一步为什么发生。
先做那次不录的预演，每次屏幕上出现你说不清的东西就记下来——那份清单就是你的学习路线。

**2）现在开始写答辩问答手册**（约 30 题，每个答案必须能指到仓库里的具体文件）。
按提问概率排，最可能被问的：

- 攻击识别准确率多少？误报率多少？←（现在你有答案了：60/60、FPR 0/58，加范围声明）
- N=3 是不是太少？
- Gate1 是规则还是模型？规则容易被绕过吗？
- Undo 能撤什么、不能撤什么？
- 45ms 增量是相对什么基线？
- 和 Lakera / LlamaFirewall / CaMeL 的区别？
- 290 条 seed 是你们自己写的吗？怎么排除过拟合？
- 为什么该相信 Gate6 哈希链？私钥谁持有？
- 那个 0.3575 怎么解释？←（归属误配，见第二节）

**3）写一份 `CODE-MAP.md`**：D1 里每个论断 → 实现它的 `文件:行` → 证明它的测试。
大概两小时的工作量，它同时是赛题第 2 项要求的"可复现/运行说明"材料，
也是把"AI 写的"变成"我知道东西在哪"的最快路径。
